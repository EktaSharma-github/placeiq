PlaceIQ Analytics: Segmenting Students for Placement Support¶

FDS course project, Phase 4. The PlaceIQ database (Phases 1–3) stores every application, interview and offer of a placement season in 22 BCNF tables. This notebook answers one question with that data:

Which kinds of students does the current placement process serve badly, and what should the committee do for each kind?

Workflow

  1. SQL first. Descriptive statistics and cross-tabs run inside PostgreSQL (07_analytics.sql, queries A1–A5). Only aggregates leave the database.
  2. Feature engineering in SQL. The view v_student_features turns six normalized tables into one row per student.
  3. Statistics. Correlation, ANOVA and χ² tests tell us which features carry signal before we fit any model.
  4. k-means clustering on profile features, with k picked by elbow and silhouette.
  5. Write back. The cluster labels go into the tables segment and student_segment, so SQL can query them (S1, S2).
  6. Threshold trade-off. A logistic model of P(offer) shows how the threshold t trades false positives against false negatives.

The data is simulated (seeded, reproducible) by 04_data.sql and loaded through the real triggers. The conclusions are about this simulated campus, but the method transfers unchanged to real data.

2. Feature engineering: v_student_features¶

Feature engineering means turning the problem into data, using domain knowledge. A placement committee sees five things about a student early in the season:

Feature Why it should matter Built from
cgpa Recruiters' first filter (A2) student
tech_score Analytics roles screen on Python, SQL, ML, … student_skill ⋈ skill
biz_score Consulting and finance roles screen on cases, Excel, communication student_skill ⋈ skill
applications You can't get an offer you didn't apply for application
interview_rate Share of applications that reached an interview (CV quality) application, interview

Outcomes (offers, accepted_offer, best_ctc_lpa) are not clustering inputs. We cluster on the profile and then check whether the segments differ in outcomes. Clustering on outcomes would make "students with many offers do well" true by construction.

The view runs one SQL statement over six tables. The single SELECT below is the only time student-level data leaves the database.

  • Point-biserial correlations: CGPA and the number of applications are significantly associated with getting an offer.

4. k-means clustering¶

Why scale first? k-means uses Euclidean distance. Unscaled, applications (0–20) would swamp interview_rate (0–1). StandardScaler puts every feature on mean 0, SD 1, so each feature gets an equal vote.

Choosing k: the elbow in the within-cluster sum of squares (inertia), checked against the silhouette score (how much closer each point is to its own cluster than to the next one; higher is better).

5. Do the segments differ in outcomes?¶

The segments were built without looking at offers. If they still differ sharply in placement outcomes, the profile features capture something real.

Reading the outcome test. The χ² test rejects independence (p ≪ 0.05): segment membership and getting an offer are strongly associated, so the clusters are meaningful, not just geometry.

Segment Who they are What the committee should do
High-Achieving Generalists High CGPA, business skills, apply widely Nothing urgent. Help them choose between offers
Tech Specialists Almost all PGDBA, strong technical skills, highest CTC Steer them towards analytics roles, where their skills match the demand in A4
Selective Appliers Apply to very few roles but usually reach interview; still no offers Broaden their applications. Their CVs work, but they apply to too few roles
At-Risk Lower CGPA, few applications, rarely reach interview Priority group: CV review, then mock interviews (query S2 lists them by name)

The "Selective Appliers" are the non-obvious finding. A CGPA cut-off would never flag them, because their CGPA is near average. The clusters found them through behaviour.

6. Write the segments back to the database¶

The labels belong in the database, not in a CSV on one person's laptop. One transaction replaces the old segmentation: either every student gets the new label, or nothing changes.

seg_id = {n: i for i, n in enumerate(ORDER)}
member_rows = [{"student_id": int(s), "segment": seg_id[n]} for s, n in zip(df["student_id"], df["segment_name"])]

with engine.begin() as c:                       # BEGIN ... COMMIT (ROLLBACK on any error)

                   "VALUES (:segment, :segment_name, :description)"), seg_rows)

7. The threshold t: false positives vs false negatives¶

Classification gives a probability, P(offer | profile), and someone has to pick a threshold t to turn it into a decision. Here the decision is "flag this student for support if P(offer) < t". The table shows the trade-off:

  • t too low: we miss students who needed help and got no offer (false negatives).
  • t too high: we spend workshop seats on students who would have been fine (false positives).

Probabilities are 5-fold cross-validated, so every student is scored by a model that never saw them.

Reading the threshold. The committee sets t according to which mistake costs more. Missing a student who ends up with no offer is worse than one extra workshop seat, so a higher t (about 0.6–0.7) is defensible. The coefficients agree with the clusters: CGPA and the number of applications have the largest positive effects on P(offer), while interview rate on its own adds little.

8. Conclusions¶

  1. The DBMS did most of the analytics work. Statistics, cross-tabs, the funnel, skill gaps and the whole feature matrix are SQL. Python received 177 rows × 5 features, not thousands of raw records.
  2. CGPA matters but isn't enough. The placement rate rises from 0% to 56% across CGPA bands, yet behaviour (how many roles a student applies to) separates the segments that CGPA can't.
  3. Four segments, four actions. The k-means segments, built without outcome data, differ significantly in placement (χ² test). Two of them, Selective Appliers and At-Risk, need different help.
  4. Back into the database. The labels live in BCNF tables with foreign keys, so S2 turns the analysis into a weekly to-do list for the committee.

Limitations. The data is simulated, so the effect sizes reflect how 04_data.sql generated it. The final cycle is still in progress, so the outcomes are a snapshot. A silhouette of about 0.3 means the segment boundaries are soft, so treat borderline students individually.
